# LAMBDA Workbench

A local web front-end for the LAMBDA language, built with Model–View–Controller.
Load or type a program written as a `d0exp` constructor expression, check it
for undeclared variables (**Lint**), evaluate it (**Interpret**) and read the
results in the browser. **Type-check** and **Compile** are placeholders, and
**Execute** stays disabled until a compiler produces generated code.

- How it is built: [ARCHITECTURE.md](ARCHITECTURE.md)
- How it is tested: [TESTING.md](TESTING.md)
- Sample inputs and their expected outcomes: [samples/README.md](samples/README.md)

## Requirements

- Python 3.12 or later (developed and tested with Python 3.14.8 on macOS)
- Flask 3.1.3 and pytest 9.1.1, pinned in `requirements.txt`
- A current browser with JavaScript enabled (tested with Google Chrome 154)

## Setup

From the repository root:

```bash
cd assigns/04/MySolution
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

On Windows, use `python -m venv .venv`, then `.venv\Scripts\pip` and
`.venv\Scripts\python` in the commands below.

## Run

```bash
.venv/bin/python run.py
```

Open **http://127.0.0.1:5000**. The server listens only on the loopback
interface. Stop it with Ctrl+C.

On macOS, the AirPlay Receiver also uses port 5000. If the page answers
"403 Forbidden", turn off System Settings → General → AirDrop & Handoff →
AirPlay Receiver, or change `PORT` in `run.py`.

## Test

```bash
.venv/bin/pytest -v
```

177 tests run in about 5 seconds. They need no browser and no running
server. The browser smoke test and the mapping from requirements F1–F10 to
tests are in [TESTING.md](TESTING.md).

## Input format

The input is a single Python-style constructor expression of type `d0exp`,
for example:

```python
D0Eop2("+", D0Eint(20), D0Eint(22))
```

- **Constructors:** `D0Eint(int)`, `D0Ebtf(True|False)`, `D0Evar("name")`,
  `D0Eop1("op", e)`, `D0Eop2("op", e1, e2)`, `D0Elam("x", body)`,
  `D0Efix("f", "x", body)`, `D0Eapp(fun, arg)`, `D0Eif0(cond, then, else)`,
  `D0Elet("x", value, body)`, `D0Epair(e1, e2)`, `D0Epfst(e)`, `D0Epsnd(e)`.
- **Operators:** one-argument `+1` and `-1`. Two-argument `+ - * / < > <= >= == !=`.
  Unknown operator names are accepted when the source is read and reported
  when the program runs.
- Comments (`#`), line breaks and indentation are allowed. Arguments are
  positional only.
- The text is never run as Python. A restricted reader parses it and accepts
  only these constructors with literal arguments.

## Limits

| Limit | Value | When exceeded |
| --- | --- | --- |
| Source size | 64 KiB (UTF-8 bytes) | Upload or Apply is rejected. The previous source is kept. |
| Interpret time | 5 seconds | The run is stopped and reported as a backend failure. Retry is available. |
| Recursion depth | About 160 nested calls (factorial of 164 works, 165 does not) | Reported as "Interpreter recursion limit exceeded". |
| Uploads | UTF-8 text only | Rejected with the position of the first invalid byte. |

## Demonstration

Each step below can be reproduced with the canned examples or the files in
`samples/`.

**1. Factorial and Fibonacci.** Choose **Factorial (canned)**. The page shows
`Factorial (canned) · revision 1`. **Lint** reports *No free variables
found.* **Interpret** shows *Interpret is running…*, then
`D0Vint(arg1=3628800)`. Choose **Fibonacci (canned)**. It becomes revision 2,
earlier results are cleared, and **Interpret** gives `D0Vint(arg1=55)`.

**2. An undeclared variable, then a fix.** Choose **Manual input**, type
`D0Evar("x")` and choose **Apply changes**. **Lint** reports a *language
error*: *Undeclared variable(s): x*. Edit the text to
`D0Elet("x", D0Eint(42), D0Evar("x"))` and apply it. **Lint** now finds no
free variables, and **Interpret** gives `D0Vint(arg1=42)`.

**3. A runtime failure after a successful Lint.** Upload
`samples/division-by-zero.txt` with **Choose File…**. **Lint** passes because
every variable is declared. **Interpret** reports a *language error*:
*Runtime error*, `ZeroDivisionError: division by zero`. Lint only checks that
names are declared. It never runs the program, so it cannot see what happens
at runtime.

**4. Placeholders and Execute.** **Type-check** reports *Type checking is not
yet implemented.* **Compile** reports *Compilation is not yet implemented.*
and *No generated code was produced, so Execute is unavailable.* **Execute**
stays disabled, with the explanation *Execute runs code generated by Compile.
It is unavailable until compilation is implemented and produces an artifact
for this source.*

**5. A bounded run.** Upload `samples/slow-fibonacci.txt` and choose
**Interpret**. After 5 seconds it reports a *backend failure*: *Timed out
after 5 s*. The controls then work again.

## Known limitations

- The server keeps one shared state. Several tabs show and change the same
  source, and restarting the server clears it.
- The application is local and single-user. It has no accounts and does not
  protect against other programs on the same machine sending it requests.
- Function values are shown in full, including their environment, so a
  result such as a lambda can be long.
- If a parenthesis is left unclosed across several lines, the syntax error may
  point to line 1 instead of the line where the parenthesis was opened.
- No automated test runs the JavaScript, because no JavaScript runtime was
  available. `app.js` is checked by reading it as text, and its behavior was
  verified with the manual browser smoke test.
- Flask's built-in development server is used. It is not meant for public
  deployment.

## Project layout

```text
run.py                  start the server on 127.0.0.1:5000
lambda_web/
  __init__.py           create_app: builds the app and chooses the backend
  model/session.py      Model: state and rules
  controller/           Controller: JSON routes, state to JSON, canned examples
  view/                 View: page template, script, stylesheet
  backend/              contract, LAMBDA adapter, restricted reader, lambda1.py
samples/                example programs, including error cases
tests/                  automated tests
```

## Reflection

MVC helped most by letting me test each piece on its own. The model is plain
Python, so every rule about revisions, drafts, validation and the busy state
could be checked in milliseconds without starting a server or opening a
browser. Since the controller talks to the backend only through a contract,
I could swap in a fake backend that crashes, blocks or pretends to compile,
and test failure, retry and the Execute path without touching the view. The
same separation kept the view safe to restyle, since the tests check structure
and element IDs rather than appearance.

Separation was hardest at the boundaries between layers. Deciding who should
call the backend took the most thought. I chose the controller, which meant a
three-step begin, run and finish protocol, but it kept the model free of
backend code and kept long interpretations from holding its lock. Busy
feedback ended up in two places: the script shows that an action is running
immediately, while the model owns the real busy flag. Keeping the editor's
draft in sync was also tricky, because an edit request that arrived after
Apply could have recreated a stale draft. Validation is spread across the
reader, the model and Flask's request limit, which is correct but means three
places to look.

The change this architecture makes easiest is the next step of the project: a
real type checker or compiler. It only needs a new backend and one change in
create_app. Storing generated code per revision, invalidating it and handing
it to Execute already work and are tested, so the controller and the view
would not change at all.
